Arquitectura actual

El runtime de IA se organiza por roles. El Backend API funciona como capa de control, el RAG local recupera evidencia desde documentos, el runtime de modelos genera respuestas y Telegram puede actuar como otro cliente del mismo backend. El frontend no lee SQLite, PDFs ni chunks directamente.

Modo principal

Frontend
   -> Backend API
        -> RAG local
        -> Runtime de modelos

Diagnostico de fallos

Connection refused

El servicio no esta escuchando en ese puerto.

Timeout

Firewall, IP incorrecta, ruta de red o servicio no accesible.

CORS error

El origen del frontend no esta permitido por el Backend API.

NO_EVIDENCE_FOR_ANSWER

RAG no encontro evidencia usable; el fallback puede responder con conocimiento del modelo.

RAG_SERVICE_UNAVAILABLE

El servicio RAG remoto esta caido; solo aplica al modo distribuido.

sqlite no such table documents

Fallo antiguo ya protegido; si reaparece indica DB o esquema invalido.

LAN opcional

Este modo existe para aprender sistemas distribuidos en LAN. No es el runtime principal recomendado: aumenta superficie de debug y separa FastAPI del corpus RAG local.

Modo distribuido experimental

Frontend / cliente LAN
   -> Servicio RAG
   -> Runtime de modelos

Notas operativas LAN

CORS

Permitir solo origenes de desarrollo concretos. Evitar * salvo laboratorio muy controlado.

IP fija / DHCP reservado

Reservar una direccion estable para el servidor reduce fallos por cambios de red.

Firewall

Abrir unicamente los puertos necesarios en la LAN confiable.

Puertos esperados

Documentar los puertos de Backend API, Servicio RAG y Runtime de modelos en la configuracion de despliegue.

Runtime recomendado

El modo all-in-one sigue siendo la ruta principal: menos piezas, corpus local y menos puntos de fallo.

Sin red nueva

Esta pestana solo documenta el modo; no crea llamadas ni endpoints adicionales.
